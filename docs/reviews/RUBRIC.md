# 审查口径（所有审查员共用）

> 本轮目标：**全面审查各个游戏（模板 × 关卡）的流程与交互**，找出"玩家靠观察就能理解规则、却被迫走提示/引导/仪式化流程"的地方，以及"答案填写方式不直观"的地方，给出简化方案。
> 本轮 **只出方案，不改代码**。任何审查员都不得修改 src/ 下任何文件。

## 0. 交付物

写入 `.scratch/review/<你的名字>.md`，结构见 §4。每个结论必须带 `file:line` 证据；没有证据的猜测不要写。

## 1. 背景事实（已由 Lead 核实，可直接引用）

- 游戏 = 模板（pattern/rule/construct/simulate/experiment/argue）× 20 个关卡内容。
- 统一流程：工具操作 → 写 `checkpoints` → `run`（可选）→ `submit` 判定。
- 判定顺序（docs/01 §5.1）：缺 artifact → 缺 checkpoint（missingEvidence）→ 约束失败 → 迁移门失败 → 通过。
- 宿主外壳 `apps/site/src/views/WorkshopView.vue` 负责：情境条(intro/prompt)、进度条(evidencePlan 步骤)、失败横幅、GuideBubble 引导、底部 运行/提交/重来。
- `GuideBubble` 的内容 = `evidencePlan[].descriptionKey`，即"关卡把内部步骤名念给玩家听"。
- 工具卡是手风琴（一次只展开一张），首张卡默认展开。
- 20 关里 16 关 `hasCanvas=false`（只有 pattern/rule 有画布）。
- 已有 e2e 用例含真实点击通关序列，可直接当"当前最少点击数"的实测口径（`e2e/level.spec.ts`、`e2e/m1.spec.ts`）。

## 2. 每个游戏必须回答的 8 个问题

1. **观察可得性**：玩家从画布/首屏能直接看出规则吗？如果不能，缺的是哪一块信息（规则、目标、约束、判定标准）？
2. **仪式步骤**：哪些步骤玩家做了但对理解/判定没有增量信息？（典型嫌疑：强制观察格子凑数、preview、run 与 submit 重复、setCycle 与 commit 两步、先选槽再选块）
3. **答案输入形态**：当前答案怎么填？逐项标注控件类型（点选/循环切换/下拉/数字输入/两步选择/拖拽），并判断"最直接"的形态应该是什么。
4. **语义重复与状态机陷阱**：run 与 submit 是否走同一份校验？preview 是否会打掉已提交状态？失败横幅是否会被"缺步骤"吞掉？（参考 docs/11 §5 已修过的同类 bug）
5. **门禁与提示**：`evidencePlan` 的 checkpoint 是否在强制玩家走固定顺序？GuideBubble 是否只是把内部步骤名念一遍？提示是否会泄题或只是噪音？
6. **失败反馈**：失败后玩家能否立刻知道"哪里错了、下一步做什么"？还是先被 missingEvidence 拦下？
7. **简化前后对比**：给出**现在的最少交互序列**（逐动作）与**建议的最少交互序列**，以及阶段数、点击数、输入控件数的变化。
8. **不可破坏项**：证据/印章/徽章/迁移门/内容 schema/`content:check`/e2e 里，哪些是这次简化必须保住的？哪些可以在方案里明确申请调整？

## 3. 判定"该不该有提示流程"的口径

对每一关回答：**规则能否从首屏观察直接推出？**
- **能**（例：带子上已给出重复片段，缺口位置肉眼可见）→ 结论应是"取消引导/提示流程，直接暴露答题面，答案输入一步到位"。
- **不能**（例：需要理解一个反直觉的判定标准，如"贪心不一定最优"）→ 结论应是"保留最小提示，但把提示放在失败反馈里，而不是开场的步骤清单"。
- 不要一刀切：每关给出 A（观察可得）/ B（需一次点破）/ C（需分步引导）分类与理由。
