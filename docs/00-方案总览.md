# 《数思工坊》Math Mind Forge · 可执行方案总览

> 不是刷题，是锻造思维工具。
>
> 本文档把原始设想收敛成一套可以开工、可以验收、可以控制范围的工程方案。它回答四个问题：**玩家到底在做什么、系统凭什么判定他会思考、内容怎么持续生产、工程怎么落地。**

---

## 1. 一句话定位

**《数思工坊》是一款"思维工具使用场"**：玩家在可操作、可失败、可修正的情境里，反复调用六件思维工具，构造出满足约束的结构、规则、模型或论证，才能推进。通关条件不是"答对"，而是**工具产物通过校验、约束被满足、证据链完整**。

三条设计红线在工程上被翻译成可执行规则：

| 原始红线 | 工程化定义 | 怎么被机器检查 |
|---|---|---|
| 关卡不是题组 | 每关必须声明必须使用的工具产物；没有产物不能提交 | 运行时门禁 + 反刷题审计 A1 |
| 难度不沿计算量上升 | 难度只有四个轴：结构复杂度、表征抽象度、约束耦合度、迁移距离 | 关卡 schema 的 `difficultyAxis` 枚举；禁止 `number-size` |
| 反馈不指向对错 | 反馈必须绑定到结构化失败类（规则失效/结构断裂/模型缺变量/论证缺口） | 每关失败类必须有反馈文案与负例测试 |

## 2. 从原方案到可执行方案：六个改造点

原方案的产品判断是对的，问题在于"思维工具""通关""评价"都还停留在描述层。下面六件事把它变成可执行的系统。

### 2.1 六件思维工具，必须有状态、操作、产物、校验器

原方案的"模式卡、规则卡、构造块、参数旋钮、数据采集器、反例探测器"是六个名词。方案落地后，每件工具都是一套**可编程的交互原语**：

| 工具 | 玩家操作 | 产物（artifact） | 校验器 | 典型证据 |
|---|---|---|---|---|
| 模式卡 `pattern` | 标出重复单元、选周期、改变换 | 模式规则 `PatternRule` | 用规则补全/预测，迁移到换表征的变体 | 先观察后下规则 |
| 规则卡 `rule` | 拼指令块、条件、循环 | 程序 AST + 执行轨迹 | 在当前地图与若干变体地图上执行 | 规则泛化、失败后迭代 |
| 构造块 `construct` | 放置/旋转/翻转块，满足约束 | 摆放集合 `PlacementSet` | 覆盖/不重叠/对称/连通/预算；可解性搜索 | 多解、简洁性、迁移 |
| 参数旋钮 `knob` | 调参数并运行模拟 | 参数向量 + 运行指标 | 预算内指标达标；换种子仍达标 | 调参—观察—修正 |
| 数据采集器 `probe` | 采样、看表、看散点/区间 | 数据集 + 样本量 + 摘要 | 样本充分性、结论是否超出证据 | 用数据支持/否定假设 |
| 反例探测器 `counter` | 构造候选反例并测试 | 反例实例 + 失效前提 | 反例确实推翻规则/贪心/猜想 | 找到"何时不成立" |

**关键改造**：工具不是装饰，也不是提示按钮。每关必须在 `requiredToolArtifacts` 里声明"没有这些产物就不能提交"，运行时在 `submit` 时校验；反刷题审计再用"无工具提交必须失败"做第二道保险。

### 2.2 "通关"变成三道门

一关的完成判定由三层组成，缺一不可：

~~~text
门 1 · 工具门：requiredToolArtifacts 全部存在，且证据检查点满足
门 2 · 约束门：关卡约束/多解判定通过（不是与标准答案比对）
门 3 · 迁移门（可选但默认）：至少一个变体通过，或在论证关提交可检验的证书
~~~

任何一门不过，返回的不是"错了"，而是结构化的 `Verdict`：`failure.class` 指出断在哪，`missingEvidence` 指出还缺哪一步，界面用"你的规则在第 3 类地图失效"这类语言反馈。

### 2.3 难度只有四个轴

难度不再用"数字变大"制造，而是：

1. **结构复杂度**：元素数量、约束耦合、层级（单位→周期→嵌套→图）；
2. **表征抽象度**：实物/图形 → 符号 → 表格 → 参数 → 形式化规则；
3. **约束耦合度**：单约束 → 双约束 → 冲突约束 → 需要取舍；
4. **迁移距离**：同表征换参数 → 换表征 → 换规则族 → 需要新工具组合。

每个关卡必须声明 `difficulty: { structure, representation, constraint, transfer }`（各 1–5），审计拒绝 `number-size` 型难度。所谓"动态难度"是对**提示与变体选择**的调节，不是把数字调大。

### 2.4 评价变成"证据信号 + 人话报告"，不产生分数

玩家每做一次有意义的操作，运行时写一条 `EvidenceEvent`（阶段、工具、动作、产物指纹、结果、失败类、修订序号）。证据系统把它聚合成四维画像：

- **结构识别**：是否先观察再操作；能否迁移到换表征的变体；
- **规则构造**：规则是否可执行、是否泛化、失败后是否迭代；
- **模型修正**：是否选变量、是否用数据验证、是否根据结果修正；
- **边界论证**：能否给出有效反例、解释失效条件、"足够好"的理由。

画像不是分数，也不进排行榜；它驱动三件事：**思想徽章**、**思维日志**、**家长/教师报告**。报告只写"本周用了哪些工具、在哪些关卡完成了从试错到结构化的转变、下一步建议体验什么"，不写正确率与刷题量。

### 2.5 内容生产：模板 + 参数 + 变体 + 负例

原方案"每学段每主线 6–10 个核心关卡"意味着 5 学段 × 4 主线 × 6–10 = **120–200 个核心关卡**。这在质量与反刷题审核下不是一个可交付的初版范围。可执行的做法是：

- **v1.0 交付 20 个核心关卡**：5 学段 × 4 主线 × 1 关，每关 2–3 个参数变体；
- 每关由"模板 + 参数化内容 JSON + 黄金解/负例 + 反馈规则"组成；
- 长期（v1.2 起）沿"每学段每主线 2–3 关"扩张，原方案的 6–10 作为内容库目标，不作为首发门槛；
- **参数化变体用于迁移检测，不用于题海**：变体必须改变结构/表征/约束，不能只把数字改大。

这不是缩水，而是把"少而深"从口号变成唯一可执行的内容预算。

### 2.6 技术栈沿用 BambooBuddy，但不复用它的玩法

沿用（经 BambooBuddy 实测的工程纪律）：

- pnpm workspace + TypeScript strict + Vite 8 + Vue 3.5 + Pinia + Tailwind 4；
- Phaser 4.2.1（裁剪版）只出现在关卡 chunk，外壳首屏不含引擎；
- 内容 JSON + zod，构建期 `content:check`；摘要/详情拆两半，详情懒加载；
- 逻辑与渲染分离，纯逻辑可脱离浏览器单测；
- `PlatformServices` 是唯一平台出口；
- 每个关卡可无头直达、`?autoplay=1` 自动通关；
- Vitest + Playwright + 内容体检 + 体积门禁 + 一条 `pnpm verify`；
- Tauri 2 + Capacitor 8：同一份 `apps/site/dist` 喂两个原生壳；
- 无后端、无账号、本地优先、不采集儿童个人信息。

不复用（有意不同）：

- 不做宠物养成与亲密度经济；成长感来自工具库、徽章、星图与证据链；
- 不做每日任务/连续天数压力；改为"推荐下一关 + 自由工坊 + 每周回顾"；
- 不做固定 750×1334 的纯 Phaser 页面；采用 **Canvas（Phaser）+ ToolDock（Vue）双面板**，因为规则编辑器、数据表、论证板必须可读、可键盘操作、可响应式；
- 不做星星评分；完成结果只有"通过了哪些门 + 得到哪些印章"。

## 3. 玩家看到的核心循环

~~~text
进入工坊 → 读懂情境（观察） → 选一件/几件工具
        → 构造/调整（规则、摆放、参数、采样、反例）
        → 点"运行" → 看结构性后果（哪里断了/哪个指标没到/哪个前提失败）
        → 修改 → 再运行 → 通过三道门
        → 得到印章 + 思维轨迹 + 徽章进度
~~~

系统侧的同一个循环：

~~~text
LevelAction 流 → LevelRuntime（纯状态机）
              → Verdict（多解判定 + 失败分类 + 缺失证据）
              → EvidenceEvent（章节/工具/产物/失败类/修订）
              → ProgressManager（存档、徽章、推荐）
              → ReportGenerator（家长/教师报告）
~~~

**玩家不直接"提交答案"**，而是操作工具、运行、看后果。界面上没有"提交答案"按钮，只有"运行""验证结构""提交论证"这类动作。

## 4. 五个学段、四条主线的纵切

首发 20 关的矩阵（每格一关；括号内是主模板）：

| 学段 | 结构与模式 | 算法与构造 | 建模与优化 | 数据与系统 |
|---|---|---|---|---|
| 幼儿园 K | 模式修补匠（pattern） | 规则小火车（rule） | 公平分点心（construct） | 分类小站（experiment） |
| 小学低段 G1–3 | 对称补墙（pattern） | 规则工程师·路线（rule） | 公平分装（construct） | 天气记录站（experiment） |
| 小学高段 G4–6 | 铺砌挑战（construct） | 最少枚数支付（construct） | 排队模型（simulate） | 不变量侦探（argue） |
| 初中 G7–9 | 路网连通（construct） | 课程表调度（construct） | 城市调度员（simulate） | 抽样调查（experiment） |
| 高中 G10–12 | 结构不变量（argue） | 算法边界关（argue） | 胜率实验室（experiment） | 统计推断站（experiment） |

这张表在 `03-关卡设计规格` 里展开成 20 关的详细规格；`MVP v0.5` 只做其中 6 关：

1. `k-structure-pattern-path` 模式修补匠（结构）
2. `k-data-tally` 分类小站（数据）
3. `g13-algorithm-route` 规则工程师·路线（算法）
4. `g46-algorithm-payment` 最少枚数支付（算法 + 反例）
5. `g79-modeling-dispatch` 城市调度员（建模）
6. `g1012-modeling-winrate` 胜率实验室（建模 + 数据）

这 6 关覆盖 4 条主线、6 件工具中的全部 6 件、5 个模板（pattern / experiment / rule / construct / simulate）；`argue` 模板与铺砌挑战（`g46-structure-tiling`）在 v0.9 补齐。选"最少枚数支付"而不是"铺砌挑战"作为 MVP 的第 4 关，是因为支付关能用更小的界面成本验证 `construct` + `counter` 的通用能力；铺砌需要等距画布与不可能证书，单独放到 v0.9。

- `pnpm e2e` 全绿（每关 autoplay、至少 3 关真实指针、无工具提交失败、证据落盘、双语、报告、编辑器）；
- 每关通过反刷题审计的自动项（A1/A1b/A2–A4/A6–A9），并附 A5/A10 人工复核记录（见 `01` 与 `03`）；
- 体积、加载、模拟耗时在预算内；
- 用户测试记录与问题清单归档。

## 6. 成功标准（可观测，不玄学）

**产品层**

- 100% 首发关卡：无工具提交必失败；每关 ≥2 条有效解（或不可能关的可检验证明）；
- 100% 关卡：失败类有对应反馈与负例测试；没有"再仔细点/粗心/算错"这类反馈；
- 0 处计分、排行、倒计时、扣命、内购、广告；
- 用户测试中，多数玩家在第二关开始出现"先观察/先调工具再运行"的行为（具体阈值在 M1 末用 5–8 名玩家校准，写进测试报告，不预先吹数字）。

**工程层**

- 首屏 JS+CSS（gzip）≤ 85 KB；最大懒加载 chunk（gzip）≤ 280 KB；dist ≤ 4 MB（M0 建立基线后按实测校准，调整预算必须写原因）；
- 单个关卡冷进入 ≤ 2 s（中端平板，本地构建产物）；一次运行判定 ≤ 200 ms；1000 局模拟 ≤ 1 s 且不阻塞交互（分片执行）；
- 纯逻辑层 0 处 `Math.random` / `Date.now`（注入种子与时钟）；
- 游戏/工具代码 0 处 `localStorage` / `fetch` / `indexedDB`（只经 `PlatformServices`）；
- 0 个联网请求（构建产物与运行时）。
