# M1 实施规格（模板、关卡、UI、验收）

> 这是 M1 的并行施工合同。四个模板由不同 builder 负责；共享文件只由 Lead 修改。所有模板必须复用 `packages/templates/src/shared/runtime.ts` 的动作驱动运行时，不允许各写一套 submit/autoplay 逻辑。

## 1. 共享运行时

每个模板实现一个 `RuntimeAdapter<S>`（见 `packages/templates/src/shared/runtime.ts`）：

~~~ts
interface RuntimeAdapter<S> {
  initialState(detail, now): S;
  apply(state, action): { state; evidence?; error? };   // 只处理工具动作
  artifact(state): unknown | null;
  artifactSummaries(state): ArtifactSummary[];
  checkpoints(state, ctx): Record<string, boolean>;
  toolState(state): Partial<ToolStateMap>;
  validate(detail, variant, artifact): Verdict;
  actionsFor(detail, variant, artifact): LevelAction[];
  transferVariants?(detail): RuntimeVariant[];
  transferFailureClass?(detail): string;
}
~~~

`createRuntimeWithAdapter(detail, opts, adapter)` 统一处理 `run/submit/reset/autoplay`、缺失证据、运行记录、transfer 门、工具使用计数。模板只写 `apply/artifact/validate/actionsFor`。

每个模板导出三件东西：

~~~ts
// verifier（构建期/审计用，不含 Phaser）
export const xxxVerifier: TemplateVerifier = {
  parseScript,
  validateArtifact(detail, variant, artifact): Verdict,
  actionsFor(detail, variant, artifact): LevelAction[],
  applyVariant(detail, variant): unknown,
  reachableFailureClasses(detail): string[],
};

// runtime（不含 Phaser）
export function createXxxRuntime(detail, opts): LevelRuntime {
  return createRuntimeWithAdapter(detail, opts, adapter);
}

// 关卡模块（有画布的模板才 import scene）
export function defineXxxLevel(manifest: LevelManifest): LevelModule;
~~~

### 2.1 `g13-algorithm-route` · 规则工程师·路线

- 5×5 网格；y 向上增加；起点 (0,0) 朝东；终点 (0,4)；
- 墙：(1,1)(2,1)(3,1)(1,2)(3,2)(1,3)(2,3)(3,3)；
- 星星：(2,0)(4,2)(2,4)；
- 路径：东 4 → 北 4 → 西 4；程序必须收齐 3 星并到终点；
- 关卡脚本：

~~~json
{
  "grid": { "width": 5, "height": 5, "start": { "x": 0, "y": 0, "dir": "east" }, "goal": { "x": 0, "y": 4 } },
  "walls": [{"x":1,"y":1},{"x":2,"y":1},{"x":3,"y":1},{"x":1,"y":2},{"x":3,"y":2},{"x":1,"y":3},{"x":2,"y":3},{"x":3,"y":3}],
  "stars": [{"x":2,"y":0},{"x":4,"y":2},{"x":2,"y":4}],
  "maxBlocks": 20,
  "maxSteps": 120
}
~~~

- 动作：`rule/place { block, at }`、`rule/remove { id }`、`rule/move { id, at }`、`rule/commit`；
- 程序块：`forward / left / right / collect / repeat(n, children) / if-wall(children)`；
- 两个黄金解：①展开 17 块；②用 `repeat 2 forward` 的 12 块版本；
- 变体：`rotate 90` 与 `rotate 180`（模板 applyVariant 旋转网格、起点方向、墙、星星、终点）；同一程序必须通过两个旋转变体（transfer 门）；
- 失败类：`rule-empty`、`rule-wall`、`rule-loop`、`rule-missed-item`、`rule-not-general`；
- UI RuleTool：按钮“前进/左转/右转/收集/重复前进×2/遇墙右转”，程序列表可删除/上移/下移，“提交程序”；
- testid：`rule-add-forward`、`rule-add-left`、`rule-add-right`、`rule-add-collect`、`rule-add-repeat2`、`rule-add-ifwall`、`rule-remove`、`rule-commit`、`rule-program`。

### 2.2 `g46-algorithm-payment` · 最少枚数支付

- 主任务：面额 `[1,3,4]`，目标 6，最优 2 枚（3+3）；
- 反例：目标/面额至少一个不同于主任务，且贪心枚数 > 最优枚数；正确前提 `greedy-optimal`；
- 关卡脚本：

~~~json
{
  "mode": "payment",
  "denominations": [1, 3, 4],
  "target": 6,
  "maxCoins": 6,
  "counter": { "targetRange": [1, 20], "minTargetGap": 4, "denominationPool": [1, 3, 4, 5], "premises": ["greedy-optimal", "no-1-coin", "target-residue"] }
}
~~~

- 动作：`construct/place/remove`（硬币值放在 `piece.shape` 的字符串里）；`counter/edit { patch: { ruleId:"greedy", instance:{target,denominations} } }`、`counter/test`、`counter/annotate { premiseId }`、`counter/commit`；
- 产物：`payment { coins, total, count }` + `counterexample { target, denominations, greedyCoins, optimalCoins, failedPremise }`；
- 校验：付清且枚数最优；反例独立于主任务、贪心确实更差、前提正确；
- 失败类：`construct-not-optimal`、`construct-overpay`、`counter-not-tested`、`counter-invalid`、`counter-reused-main`、`counter-wrong-premise`；
- 变体：两个 representation 变体（`v-weights`、`v-cards`，逻辑不变），使黄金解仍通过；
- UI PaymentTool：面额按钮、已放硬币列表/删除、总额/枚数；CounterTool：目标数字、面额复选框、测试、结果、前提选择、提交；
- testid：`payment-add-3`、`payment-clear`、`payment-total`、`counter-target`、`counter-denom-1`、`counter-test`、`counter-premise`、`counter-commit`。

### 2.3 `k-data-tally` · 分类小站

- 20 个图形：circle 6、square 5、triangle 6、star 3；每次采集 5 个；
- 玩家必须采满 20、手动记录统计条、提交“最多/最少”的结论；
- 关卡脚本：

~~~json
{
  "mode": "tally",
  "batchSize": 5,
  "categories": [
    { "id": "circle", "label": "圆", "token": "●", "count": 6 },
    { "id": "square", "label": "方", "token": "■", "count": 5 },
    { "id": "triangle", "label": "三角", "token": "▲", "count": 6 },
    { "id": "star", "label": "星", "token": "★", "count": 3 }
  ],
  "items": ["circle","square","triangle","star","circle","triangle","square","circle","triangle","star","circle","square","triangle","circle","square","triangle","star","circle","triangle","square"]
}
~~~

- 动作：`probe/sample`、`probe/tally { counts }`、`probe/focus`、`probe/claim { claim }`；
- 产物：`dataset { n, counts }` + `tally { counts }` + `claim`；
- 校验：n=20；tally 与 items 计数一致；claim 是 `count-compare` 且与数据一致（最多并列时 tiedWith 必须包含另一个）；
- 失败类：`probe-not-collected`、`probe-sample-small`、`probe-tally-wrong`、`probe-claim-mismatch`；
- 变体：`v-fruit`（token 换成水果）、`v-five`（增加一类，总数 25）；transfer 不做（[]）；
- UI TallyTool：大按钮“采集一把”、已采集 chip 列表、四个类别 +/- 记录、方向/类别选择、“提交结论”；
- testid：`tally-sample`、`tally-plus-circle`、`tally-minus-circle`、`tally-claim-most`、`tally-category-circle`、`tally-claim-submit`。

### 2.4 `g79-modeling-dispatch` · 城市调度员

- 6 站环线，需求固定：seed A [3,2,4,3,2,4]，seed B [2,4,3,2,4,3]；容量 10；预算 120；
- 参数：车辆 1–4、服务队 1–2、班次 60/90/120、路线 single/two-zone/fast；
- 模拟公式（纯函数，可单测）：

~~~text
capacity = vehicles * 10
routeFactor = single ? 1 : two-zone ? 0.98 : 0.94
coverage = min(totalDemand, capacity * routeFactor) / totalDemand
baseWait = 30 - vehicles*4 - teams*2 + (shift===60?6:0) + (route==="two-zone"?1:0) + (route==="fast"?2:0)
wait(seedA) = max(4, baseWait); wait(seedB) = max(4, baseWait + 1)
cost = vehicles*25 + teams*10 + shift*0.2
~~~

- 目标：A 覆盖率≥0.9、等待≤18、成本≤120；B 覆盖率≥0.85、等待≤20；
- 动作：`knob/set`、`knob/run`（一次运行 A/B 两个种子）、`knob/reset`、`knob/commit`、`probe/focus`；
- 产物：`params` + 两个种子的 `runs`；校验重算指标，不信任手写数据；
- 至少两组可行解：3 车+1 队+90 分钟（成本 103、等待 16/17）；2 车+2 队+90 分钟（成本 88、等待 18/19）；
- 失败类：`sim-not-run`、`sim-budget`、`sim-coverage`、`sim-wait`、`sim-overfit-seed`；
- 变体：`v-layout`（站点顺序换）、`v-demand`（需求分布换），transfer 不做（[]）；
- UI KnobTool：车辆/服务队/班次/路线控件，“运行两个种子”，当前指标；MetricsTool：最近运行表 + 目标灯 + “查看指标”（派发 `probe/focus`）；
- testid：`knob-vehicles`、`knob-teams`、`knob-shift`、`knob-route`、`knob-run`、`metrics-table`、`metrics-focus`。

### 2.5 `g1012-modeling-winrate` · 胜率实验室

- 10 回合；100 资源分给 attack/defense/economy（和 100，步长 5）；
- 种子 101（A）与 202（B）；1000 局；Wilson 95% 区间；
- 模型（可调系数，但必须确定性）：

~~~text
对每个对手原型（rush 50/20/30、turtle 20/50/30、economy 30/30/40）：
  每回合玩家分：A = attack*(1+0.03*eco)  D = defense*(1+0.03*eco)
  每回合对手分：OA = opp.attack*(1+0.03*oppEco)  OD = opp.defense*(1+0.03*oppEco)
  eco 随回合增长：eco = economy*0.1*(round-1)
  噪声：mulberry32(seed*10007 + round*131 + side) 映射到 [0.9,1.1]
  A > OD 玩家得 1 分；OA > D 对手得 1 分；10 回合后分高者胜，平局 0.5
~~~

- 允许在 M1 调系数与目标：先写一个校准脚本（在一组参数网格上跑 1000 局），把“最佳策略”的胜率写进内容，目标设为比它低 2–3 个百分点；不要伪造数值。若实测达不到 55%，目标可降到 52% 并在 `docs/05` 记录；
- 动作：`knob/set`、`knob/commit`、`probe/sample { n }`、`probe/clear`、`probe/focus`、`probe/claim { claim }`；
- 产物：`params` + `dataset { n, wins }` + `claim { statistic:"proportion", value, n, ci }`；校验重算 A/B 胜率，检查 n≥1000、A 目标、区间下界、B 至少 52%；
- 失败类：`exp-not-run`、`exp-sample-small`、`exp-below-baseline`、`exp-claim-beyond-ci`、`exp-overfit-seed`；
- 变体：`v-opponents`（权重 5:3:2）、`v-resources`（资源 80、回合 12），transfer 用 seed B 检查（返回 B 变体）；
- UI SampleTool：100/500/1000 采样按钮、胜率/区间、样本量、“用这次数据下结论”（派发 `probe/claim`）；KnobTool 复用；
- testid：`sample-100`、`sample-1000`、`sample-clear`、`sample-claim`、`sample-result`。

## 3. 内容文件与登记

每个 builder 写：

1. `packages/content/src/levels/<id>.json`（摘要）
2. `packages/content/src/details/<id>.level.json`（详情）
3. `games/forge/src/levels/<id>.ts`（关卡入口，`defineXxxLevel(manifest)`）

5. `packages/toolkit-ui/src/<Component>.vue`
6. `packages/templates/src/<template>/logic.test.ts`（至少：黄金解通过、负例失败类、无工具提交失败、autoplay 通过）

详情必须包含：`tools/requiredToolArtifacts/levelScript/evidencePlan/solutions(≥2)/negativeSamples(≥3)/variants(≥2)/feedback/badges/manualAudit`。

## 6. UI 组件约定

- Props：`{ spec, runtime, snapshot, t }`（与 PatternTool 一致）；
- 用 `shallowRef` / 纯函数读 snapshot，不要深层 reactive runtime；
- 按钮是原生 `<button type="button">`，键盘可操作；
- 用 Tailwind token（`bg-card` / `text-ink` / `border-grid` 等），不新增 CSS 文件；
- 操作后不自己维护副本：以 snapshot 为准；本地只保留表单草稿；
- 所有关键按钮带 `data-testid`。

## 7. 进度与证据

- 每个工具动作都经 `runtime.dispatch`；共享运行时自动记录工具使用次数；
- 模板 `apply` 可以返回 `evidence` 草稿（phase/tool/action）；不返回也可以，共享运行时会在 run/submit 写证据；
- 不直接写存档、不直接碰 `localStorage`/`fetch`/`IndexedDB`。

## 8. 与 M0 的差异

- M0 首关的 pattern 运行时暂不迁移到共享运行时；M1 新模板必须用共享运行时；
- 共享运行时支持 transfer 门：`transferVariants` 返回变体时，submit 会逐个验证；失败返回 `transferFailureClass`（默认 `transfer-failed`）。rule 用 `rule-not-general`，winrate 用 `exp-overfit-seed`；
- runEnabled=false 的关卡由工具按钮运行，宿主隐藏“运行”；
- 无画布关卡由宿主把 ToolDock 拉满宽度。
